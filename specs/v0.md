# v0 — Initial design specification

| Field | Value |
|---|---|
| Version | v0 |
| Status | Retrospective design baseline; no executable release |
| Documented | 2026-10-13 |
| Provenance | Original user requirements and the recorded design process |
| Implementation successor | v1.0.0 |

## 1. Problem and intended outcome

An author or agency should be able to ask an assistant to understand a person, their product and their audience, then create a coherent LinkedIn personal brand and useful posts in that person's voice. A reusable skill should carry that understanding between sessions and work for multiple clients without mixing their identities or information.

The inspiration is Kleo's public knowledge/voice/strategy/writing workflow. The user's desired outcome is a close practical substitute, with a stated aspiration of more than 85% equivalence. That aspiration is not an accepted performance claim. Public feature descriptions alone cannot establish output equivalence.

## 2. Intended users and requests

- A founder building recognition around a product or service.
- An expert developing a recognizable point of view.
- An agency operator writing for several distinct clients.
- An existing client returning for one post, a revision or a performance review.

Representative requests:

1. Understand my profile and offer, then develop positioning and a content strategy.
2. Read these examples and write a post in my voice.
3. Turn this product demonstration or transcript into several distinct ideas.
4. Save this preference for future posts, but make this other change only for today's draft.
5. Review actual post results and suggest the next experiment.

## 3. Proposed capability scope

| Area | Intended behavior |
|---|---|
| Author discovery | Use accessible profile material, interviews and supplied documents to understand identity and expertise |
| Product discovery | Identify the actual offer, audience, mechanism, proof and limits |
| Voice | Learn patterns from authentic samples and client feedback; mark missing evidence |
| Strategy | Connect positioning, content pillars, audience problems and business/professional goals |
| Ideas | Produce distinct, source-grounded angles rather than generic topic lists |
| Writing | Draft, rewrite, repurpose and edit usable LinkedIn content |
| Memory | Keep durable client context and scoped corrections between sessions |
| Multiple clients | Store each author's information separately |
| Delivery | Provide clean drafts; use optional publishing tools only when authorized |
| Learning | Use available analytics and feedback to propose changes |

## 4. Conceptual workflow

1. Identify the active author and requested deliverable.
2. Load existing client context or collect the minimum missing information.
3. Inspect accessible profile/product evidence and writing samples.
4. Establish provisional positioning, voice and content direction.
5. Select an evidence-backed idea and write the requested artifact.
6. Check truth, voice, relevance and reading experience.
7. Deliver the artifact and save the relevant context/corrections.
8. Review outcomes when actual results become available.

The workflow must support a short single-post route. It must not require a complete rebrand every time the author asks for a rewrite.

## 5. Inputs and outputs

Inputs may include a profile URL or export, product pages, client statements, authentic posts, documents, transcripts, preferred language and an audience/goal brief. Missing information should remain unknown or provisional; it should not become an invented biography, customer result or opinion.

Outputs may include a profile audit, positioning brief, voice guide, content strategy, idea queue, full post drafts, source notes and performance review. The amount of work should follow the actual request.

## 6. Design constraints

- A skill supplies instructions; it does not itself grant browser access, LinkedIn permissions, private analytics or background execution.
- Use ordinary authorized tools to inspect a profile. Supplied text and a saved URL are different from an observed live page.
- Keep facts, experience, permissions and writing samples attached to the correct client.
- Do not invent client results or convert reference creators' stories into the client's personal history.
- Distinguish a one-post instruction from a permanent preference.
- Distinguish drafting from publishing and a calendar from a running scheduler.
- Keep local client data separate from the distributable skill.
- Record tool/access limitations and continue useful work where possible.

## 7. Acceptance plan

The first executable release should demonstrate:

1. A new-client brief produces useful strategy and actual drafts.
2. A single-post request produces one post without unnecessary setup.
3. Switching clients preserves identity, facts and style boundaries.
4. Durable corrections survive reload; temporary overrides stay scoped.
5. Blocked profile access is reported honestly while supplied material remains usable.
6. Unsupported numerical or first-person claims are removed or marked unresolved.
7. Local draft state is never mistaken for a completed external action.
8. Performance analysis distinguishes missing data from zero and observation from causation.

Output parity with Kleo requires matched inputs and independently reviewed outputs. Until those tests exist, report functional coverage and observed behavior separately from similarity.

## 8. Historical boundary

This document captures the initial intent retrospectively. It is not evidence that a v0 code package, model benchmark or public release existed before this repository was created. Detailed file contracts and the executable workflow belong to the v1.0.0 specification.
